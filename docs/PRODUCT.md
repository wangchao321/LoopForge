# LoopForge 产品需求草案

## 1. 目标

把售前对话中的客户诉求转化为可管理、可交付、可验收的产品需求；将发布后的产品知识提供给 FAQ 助手，并把新反馈送回需求池。

产品类别为 AI 产品交付编排平台：通过连接企业现有管理系统，统一需求标准和交付关系；通过 Loop Engine 观察进展、识别阻塞、提出调整，并在授权范围内执行和验证。连接器和自动推进的详细规则分别见 CONNECTORS.md 与 LOOP_ENGINE.md。

第一版以企业软件产品为对象。一个企业组织可以维护多个产品；需求、版本、资料和知识必须明确所属组织与产品。公开的是项目源代码，运行实例中的客户数据与业务资料默认私有。

## 2. 角色与职责

| 角色 | 主要操作 |
| --- | --- |
| 组织管理员 | 管理成员、角色、组织配置和产品权限 |
| 售前 | 发起访谈、校对 AI 需求草稿、提交需求、查看授权范围内的进展 |
| 产品经理 | 评审、合并或拒绝需求，维护方案与验收标准，安排目标版本 |
| 研发 | 估时、拆分任务、更新开发进度、关联代码与构建结果 |
| 测试与验收人 | 提交证据、登记缺陷、执行验收、签署结论 |
| 发布负责人 | 检查发布条件，发布或撤回版本 |
| 客户或支持人员 | 在授权范围内使用 FAQ、查阅已发布材料、提交反馈 |

权限按组织、产品及资源可见范围校验。首版允许同一成员兼任多个角色，但关键审批需要有明确的执行人和时间记录。

## 3. 核心流程

### 售前 AI Bot

通过对话收集业务场景、现有问题、目标用户、期望收益、优先级建议、约束和期望时间。缺失字段继续提问，不编造业务事实。输出结构化需求草稿，保留原始对话引用；由售前确认后进入需求池。客户期望时间不等于交付承诺。

### 需求池

记录标题、描述、来源、客户标识、产品、分类、价值、紧急程度、负责人、附件和验收标准。AI 可建议相似需求，人工决定合并；合并后仍保留全部来源。支持搜索、筛选、讨论、变更历史及待补充、待评审、已采纳、已拒绝、已合并状态。

### 方案设计

每个方案包含问题定义、目标、范围、排除项、业务流程、交互或原型引用、技术影响、依赖及可验证的验收标准。方案有版本与评审记录；评审通过后才能进入正式排期。排期后的范围变更需要重新评审，并明确对版本的影响。

### 开发与版本排期

一个版本可以覆盖多个需求，一个需求可拆为多个交付项进入不同版本；通过交付项记录每个版本的实际范围，避免部分交付被误标为全部完成。任务关联交付项、负责人、估时和依赖。首版先支持人工关联 GitHub Issue、PR 和提交链接；自动同步在后续实现。

Sprint 记录团队、目标、起止时间及计划工作；Release 记录版本交付范围和发布承诺。两者独立建模，允许多对多关联。Sprint 结束不自动发布 Release；未完成工作结转或版本范围调整必须符合团队授权规则，并记录原因和影响。第一版 Loop Engine 先提供观察、建议和人工批准后的内部操作，正式发布保持明确的人工作用。

### 验收

逐项记录验收标准、测试结果、证据、执行人和时间。失败项回到开发流程，重新验收；阻塞缺陷未关闭时不能发布。验收结果只对对应方案修订及构建生效，构建或范围发生变化后需要重新核对受影响的验收项。

### 发布与材料

发布清单包含版本号、代码提交、构建标识、包文件、文件大小、校验值、发布说明、安装升级说明、回滚说明和用户文档。材料也有可见范围。首版管理包文件与发布清单，不承诺自动部署客户环境。

发布条件：范围明确、必需验收通过、无阻塞缺陷、必需包和材料齐全、发布负责人审批。已发布清单固定为发布快照；更换包需要新发布记录。撤回后保留审计记录并在下载及知识入口标明失效。

### FAQ AI Bot

只检索调用者有权访问、已审核、适用于所选产品和版本的知识。回答附来源及适用版本；资料不足时明确表示无法确认并引导提交反馈。内部方案、客户对话和未发布能力不得自动进入客户知识库。知识撤回后停止检索，相关缓存失效。FAQ 新问题经人工确认后形成新需求。

## 4. 状态设计

需求状态：草稿 → 待评审 → 待补充 / 已采纳 / 已拒绝 / 已合并。

交付项状态：待设计 → 方案评审 → 待排期 → 待开发 → 开发中 → 待测试 → 待验收 → 验收通过 → 已发布。测试或验收失败可退回开发中，并记录原因。需求是否交付由全部约定交付项决定，独立于需求评审状态。

版本状态：规划中 → 开发中 → 验收中 → 待发布 → 已发布 → 已撤回。待发布或已发布版本发生范围变化时创建新修订，并重新执行相关门禁。

## 5. 首版验收场景

1. 售前完成一次示例对话，检查 AI 草稿，确认后在需求池看到需求及对话来源。
2. 产品经理合并重复需求，两个原始来源均可追溯；补全方案与验收标准并完成评审。
3. 将需求拆为交付项，安排目标版本并创建开发任务；能反查需求、方案、版本之间的关系。
4. 测试记录失败证据后，版本发布被阻止；研发修复后重新验收并保留历史记录。
5. 发布负责人补齐包、校验值和材料，通过门禁并发布固定快照；可下载授权材料。
6. FAQ 基于发布后的授权文档回答并展示引用；对尚未实现的能力明确表示无依据。
7. FAQ 反馈经人工确认回到需求池，形成闭环。
8. 另一个组织的成员无法读取该组织的对话、需求、包或知识；越权尝试不会泄露资源是否存在。

## 6. 首版边界

首版包含组织与角色、产品管理、文本访谈、需求池、方案修订、交付项、任务、版本、验收、材料管理和有引用的 FAQ。暂缓复杂容量预测、自动编码、自动部署、多渠道机器人、计费和高级组合管理。企业 SSO、复杂审批策略和高可用部署在后续补齐，不能将首版称为企业生产就绪。
